# CurveSmear 0.1.7 計測結果（2026-09-14）

現行CPU処理の主な負荷は、各ピクセルからカーブの全セグメントを探索する部分だった。短いカーブは約69ms、長い弧は約896ms。最初の高速化は近傍候補の絞り込みを対象にするのが妥当。

今回は計測のみ。製品コードと配布バイナリは変更していない。過去の約55msというユーザー報告とは素材・パスが異なり、速度の増減を直接比較するものではない。

## ネイティブ計測

1920×1080、Core i7-14700F、1スレッドを論理CPU 2（Pコア）へ固定。MSVC 14.50.35717、/O2、/MT、SDK 25.2。プロセスの優先度は通常。GPUは使用しない。

現行の `renderPixels` をそのまま呼び出す。入力は生成したRGBA模様、マットは縦縞の白黒。Amount=250、Flat、Feather=55%、Streak=65%、Frequency=17、Keep Original=0、幅プロファイルは均一100%。パスは解析曲線を約3px間隔の折れ線へ変換したもの。

初回呼び出しを別記録した後、9回の中央値を集計。入力・出力の確保と生成、ファイルI/Oは計測区間に含まない。ここでいう初回は初期化済みメモリへの最初の呼び出しであり、AE起動・素材読み込み・ディスクキャッシュのコールド計測ではない。CSVのp95はnearest-rank方式で、9回では最大値に当たる。厳密な長期テール遅延の推定には使わない。

初期のCPU固定なしの試行では時間が大きく変動したため、中断して採用しなかった。Pコア固定は比較用プログラムだけの設定であり、AEの通常スケジューリングを再現してはいない。

## 負荷の切り分け

| ケース | 現行レンダー全体 | 探索パス | 変位計算パス | サンプリング・合成パス |
|---|---:|---:|---:|---:|
| 短い弧、Nearest | 68.53 | 59.74 | 21.90 | 4.84 |
| 短い弧、Linear＋マット | 75.78 | 60.99 | 22.06 | 9.59 |
| 長い弧、Nearest | 896.36 | 870.21 | 34.63 | 7.08 |
| 長い弧、Radius 250 | 1831.42 | 1756.01 | 79.54 | 18.78 |

単位はms。後ろの3列は原因調査用に処理を分け、途中結果を配列へ保存・読み出しした独立測定。余分なメモリアクセスとコンパイラーの最適化差があるので、足し算して全体時間にしたり、厳密な占有率を算出したりしない。ネイティブ全ケースで、分割版の座標・影響率と最終画像が現行実装に全ピクセル完全一致することを確認した。

短い弧では約14.5万ピクセル×183区間＝約2660万回、長い弧では約83.3万ピクセル×572区間＝約4.77億回の候補評価を行う。長い弧の場合、全区間を探索したピクセルのうち影響範囲に入るのは約26.7%。探索候補と処理対象をタイル単位で絞る余地が大きい。

解析曲線の生成・再サンプリング・プロファイルLUT準備は約0.3〜0.4ms程度だったが、これはテスト用の準備処理。AEのPathQuery/PathDataやcheckoutにかかる時間を測った値ではない。

## AE 26.3 内の計測

別の空プロジェクトで、1080p PNG→CurveSmear→TIFFを6フレームずつ書き出し、3回の中央値を取得。各回でAEキャッシュを消去し、Seedをフレームごとに変える。MFRはスクリプト中にoff/onを明示して比較。AEはPコアへの固定を行わない。

ホスト側のパスは2点の3次Bezier（頂点700,540→1200,540、接線±166.67,-133.33）。ネイティブ側のsin曲線とは厳密に同じパスではない。マットは白黒縦縞。入力とマットは `prepare-benchmark.py` で生成する。

| 条件 | MFR off | MFR on |
|---|---:|---:|
| Amount=0、8bpc | 42.83 | 41.50 |
| 短い弧、8bpc、Nearest | 115.50 | 58.50 |
| 短い弧、8bpc、Linear＋マット | 115.33 | 62.50 |
| 短い弧、32bpc、Linear＋マット | 147.33 | 89.00 |

数値は「6フレーム全体の所要時間÷6」のms/frame。素材準備・色深度変換・TIFF出力・レンダーキュー開始終了を含む連番の実効時間で、1枚の描画レイテンシやComposition Profilerのエフェクト単体時間とは異なる。特にMFR onの値を編集時の応答時間として扱わない。短い6フレームの試験なので長時間レンダーの定常スループットは未評価。

出力検証：Amount=0とNearestの間に67,726ピクセルの差、Seed=0と5の間に62,275ピクセルの差があり、変形とフレーム更新が実行されていることを確認。8bpcのNearestとLinear＋マットでは、MFR off/onの代表フレームが完全一致した。

32bpcプロジェクトのホスト出力はテンプレートによって8bit TIFFになっており、最大1/255の差が生じた。同じMFR offの反復同士にも同量の差があるため、これだけでMFRによる描画差とは判断できない。書き出し時の量子化・ディザが候補で、HDRの厳密なホスト差分検証にはEXR等のfloat出力が必要。ネイティブ32bpcの分割処理と現行処理は完全一致済み。

起動ログに `TempDisableGPU3 ... skipping GPU3` が記録された。今回のCPU計測は完了したが、将来のGPU試作ではこの状態と実際にAEから提供されるGPUフレームワークを確認する。今回GPU設定は変更していない。

## 再実行

リポジトリ直下、MSVCがPATHにある環境で実行する。以下はプラグインを再ビルドしない。

```powershell
python native/build.py --benchmark-only
.\build\Benchmark.exe test-output\benchmark.csv 9 2
```

引数はCSV出力先、反復回数、任意の論理CPU番号。CPU番号は実行するPCの構成に合わせる。4番目の追加引数で `,short_8_nearest,long_8,` のようにケース名を両端カンマ付きで指定できる。省略すると全ケース。

AE側は次を実行する。`BenchmarkCurveSmear.jsx` は空プロジェクト以外では中断する。

```powershell
python scripts/prepare-benchmark.py
& 'C:\Program Files\Adobe\Adobe After Effects 2026\Support Files\AfterFX.com' -noui -r "$PWD\scripts\BenchmarkCurveSmear.jsx"
```

ネイティブ測定データ：`017-2026-09-14-run1.csv`、`017-2026-09-14-run2.csv`。ホスト測定データ：`017-2026-09-14-ae26.csv`。環境とソース/配布バイナリのSHA256：`017-2026-09-14-environment.json`。
